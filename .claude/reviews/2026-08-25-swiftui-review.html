High line 106–116 correctness Fixed 69dda8a Fixed 8c73ba9
save(context:) ignores the context it is given.

All twenty call sites pass a context which is then discarded in favour of container.viewContext. Today every caller happens to pass the view context, so nothing breaks — but the parameter is a lie, and the first background context added to this app will save to the wrong place with no error. The DispatchQueue.main.async also defers every save by a runloop tick, which is why several call sites have grown their own asyncAfter delays to compensate.

Before
func save(context: NSManagedObjectContext) {
    if context.hasChanges {
        DispatchQueue.main.async {
            do {
                try container.viewContext.save()
            } catch {
                dataLogger.error("…")
            }
        }
    }
}
After — on the context's own queue
func save(context: NSManagedObjectContext) {
    guard context.hasChanges else { return }
    context.performAndWait {
        do {
            try context.save()
        } catch {
            dataLogger.error(
                "[CoreData:save] \(error.localizedDescription)"
            )
        }
    }
}
Landed in two steps. 69dda8a saved the context it was handed; the DispatchQueue.main.async stayed. That deferral turned out to be load-bearing in the wrong direction — it left the store a main-queue turn behind the caller, so anything reading the store straight after a write saw stale data. It is why EventPropertyDetailsSheet grew asyncAfter(0.2) waits before reloading, and why the post-mutation refreshes could not move to a background context. 8c73ba9 replaced it with performAndWait, which is reentrant — a caller already on the context's queue saves in place. That changed when around twenty call sites commit, so it is the single riskiest commit on the branch: see Check 02.

persistentStoreDescriptions.first!.url! sits on the migration path, so a missing store description crashes before the first frame — with no log and no recovery. Since this is genuinely unrecoverable, at least make it say so.

High line 479–490 concurrency Fixed 505fa66
Core Data objects are read from a global dispatch queue.

store.enumerateContacts runs on DispatchQueue.global, and its closure reads self.wrappedName and hands self to setContactID(for:), which reads penpal.id. Both are NSManagedObject property accesses from a thread that doesn't own the context. This is exactly what -com.apple.CoreData.ConcurrencyDebug 1 exists to catch, and it will become a hard compile error under Swift 6. Read the values out before leaving the context, and pass plain Sendable types across.

Before
DispatchQueue.global(qos: .userInitiated).async {
    try store.enumerateContacts(with: request) { contact, _ in
        // ⚠️ self.wrappedName off-queue
        if contact.fullName == self.wrappedName {
            // ⚠️ reads penpal.id off-queue
            UserDefaults.shared.setContactID(
                for: self, to: contact.identifier
            )
        }
    }
}
After
// snapshot on the context's own queue first
let name = wrappedName
guard let penpalID = id else { return }

Task.detached(priority: .userInitiated) {
    var match: String?
    try? store.enumerateContacts(with: request) { contact, _ in
        if contact.fullName == name {
            match = contact.identifier
        }
    }
    guard let match else { return }
    await MainActor.run {
        UserDefaults.shared
            .setContactID(forID: penpalID, to: match)
    }
}
Also add — an ID-based overload so no managed object crosses the boundary
extension UserDefaults {
    func setContactID(forID uuid: UUID, to identifier: String) {
        var map = penpalContactMap
        map[uuid.uuidString] = identifier
        penpalContactMap = map
    }
}

Helpers/AppPreferences.swift

2 findings · 21 lines
High line 11–19 data-flow Fixed 6da712a
@AppStorage inside an ObservableObject does not drive view updates.

This is the documented dead end. @AppStorage's change-tracking only works when the property wrapper lives on a View; here the didSet fires after the value has already changed (SwiftUI needs willSet), and a write to the same key from anywhere else — the Settings sheet's own @AppStorage, say — never fires it at all. StatsView and PenPalList both depend on trackPostingLetters, so the setting can silently fail to propagate. The class earns nothing; delete it and read the key directly wherever it's needed.

Before
class AppPreferences: ObservableObject {
    static var shared = AppPreferences()

    @AppStorage(.trackPostingLetters,
                store: .shared)
    var trackPostingLetters = true {
        didSet { objectWillChange.send() }
    }
}
After — in each view that needs it
@AppStorage(UserDefaults.Key.trackPostingLetters,
            store: .shared)
private var trackPostingLetters = true
Knock-on cleanup: removing the class also removes the .environmentObject(AppPreferences.shared) injection and the @EnvironmentObject var appPreferences declarations in PenPalList.swift:14 and SettingsList.swift:33 — neither of which currently reads anything off it.
Low line 13 concurrency
static var shared is a mutable global.

A data race under Swift 6's strict concurrency checking. If the type survives at all, it should be static let. The same applies to PersistenceController.preview (static var, line 25).

Found since · 2 September 2026

The Pen Pal who moved section

None of these were in the original review. They came out of one question: after a backup and restore, a Pen Pal moved from Nothing to do to You have post to send. The restore hadn't changed the events — it had recalculated them. PenPal.lastEventType is a stored cache of what the event history says, and it had drifted; restoring re-derives every Pen Pal, which is why a restore is where you notice.

It has to be stored, not computed: the list sections are @FetchRequests predicated on lastEventTypeValue, and you can't predicate on a derived value. So the fix isn't to remove the cache — it's to stop it drifting, and to repair it when it does. Three ways it drifted:

High Data/Event+Extensions.swift:134 correctness Fixed 6d161ed
Deleting an event recalculated the Pen Pal before the delete had settled.

Two failures in three lines. A fetch returns objects marked for deletion until pending changes are processed, so getLastEvent could hand back the very event being deleted — and context.delete nullifies the event's penpal relationship, so self.penpal could already be nil and nothing recalculated at all. Either way the Pen Pal kept the state it had before the delete. Delete the newest event and they stay wherever they were.

Before
func delete(in context: NSManagedObjectContext) {
    context.delete(self)
    // ⚠️ may fetch the deleted event; penpal may be nil
    self.penpal?.updateLastEventType(in: context)
    // …save
}
After
func delete(in context: NSManagedObjectContext) {
    let penpal = self.penpal
    context.delete(self)
    context.processPendingChanges()
    penpal?.updateLastEventType(in: context)
    // …save
}
Medium PenPal+Extensions:192, 239, 531 · Event+Extensions:225 · PenPalView:33 correctness Fixed c6285cd
Every event fetch sorted on date alone.

Two events at the same instant came back in whatever order the store held them — and that order isn't stable. Rewriting the rows, which is exactly what restoring a backup does, can swap them. getLastEvent walks that list to decide the Pen Pal's state, so which of the two counted as “last” could change underneath you. The event id is now a secondary key, matching each fetch's direction so the ascending and descending orders stay mirror images.

Deliberately arbitrary rather than clever: typeValue would have been the semantic choice, but the raw values don't support it — written(1) → sent(4) reads forwards while inbound(3) → received(2) reads backwards, so it would order one chain right and the other wrong.

Before

    NSSortDescriptor(key: "date", ascending: false)
]
After
fetchRequest.sortDescriptors = [
    NSSortDescriptor(key: "date", ascending: false),
    NSSortDescriptor(key: "id", ascending: false),
]
High Data/PenPalStateRepair.swift · new data-flow Fixed 5823db5
A stale lastEventType merged in from another device was never re-derived.

CloudKit mirrors the cache like any other attribute, and under NSMergeByPropertyObjectTrumpMergePolicy an older copy from another device can win the merge. Nothing then re-derives it until that Pen Pal's next event, so they sit in the wrong section indefinitely — until something recalculates, which is what a restore does.

PenPalStateRepair watches .NSPersistentStoreRemoteChange — debounced, because a CloudKit import posts in bursts, and hopped to main because the repair works on the view context — and re-derives each Pen Pal from its events, writing back only the ones that disagree. It also runs once at launch, for merges that landed while the app was closed. Remote-change notifications are off by default, so the store descriptions now ask for them before the stores load.

It converges rather than ping-ponging between devices: a Pen Pal whose stored state already matches its events is left untouched, setLastEventType skips writes of identical values and save returns early on hasChanges — so a device that agrees writes nothing, and there is no repair for the other device to import back.

Data/PenPalStateRepair.swift
private init() {
    NotificationCenter.default
        .publisher(for: .NSPersistentStoreRemoteChange)
        .debounce(for: .seconds(2), scheduler: DispatchQueue.main)
        .sink { [weak self] _ in self?.repair() }
        .store(in: &disposables)
}

func repair() {
    let context = PersistenceController.shared.container.viewContext
    var repaired: [String] = []
    for penpal in PenPal.fetchAll(from: context) {
        let before = (penpal.lastEventType, penpal.lastEventDate,
                      penpal.lastEventLetterType)
        penpal.updateLastEventType(saving: false, in: context)
        if before != (penpal.lastEventType, penpal.lastEventDate,
                      penpal.lastEventLetterType) {
            repaired.append(penpal.wrappedName)
        }
    }
    guard !repaired.isEmpty else { return }
    PenPal.updateAppState()
    PersistenceController.shared.save(context: context)
}
